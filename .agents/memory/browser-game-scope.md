---
name: Browser API and game scope
description: Product boundary for public API work versus other feature work.
---

The public browser homepage stays unchanged. After sign-in, users land in THE OFFICE: a private desktop workspace with one blank widget and up to nine selectable, movable features; mobile shows one feature at a time. The downloadable Desktop OS stays separate: its nine native game widgets open from in-world furniture and terminals and use game artwork, never browser React pages. The office simulation is a free game feature and should be promoted on `/desktop` with authentic gameplay footage that autoplays muted and loops.

The only browser page connected to the desktop experience is the `/desktop` download page. The downloadable OS app is computer-only for macOS, Windows, and Linux; there is no phone app.

Paid features in the game version remain subject to their existing paid entitlement gates. Downloading the public game client does not unlock them.

**Why:** The user clarified that the public homepage must remain promotional, signed-in browser users should go directly to work, and the native game must use furniture/terminal entry points and game visuals rather than replacing or embedding the browser workspace.

**How to apply:** Keep the professional browser tools in the browser, share backend data where needed, and build the gameplay client’s own screens and interactions. Connect desktop marketing/downloads through `/desktop` only. List computer builds for macOS, Windows, and Linux; do not present a phone app. Preserve existing in-game entitlement checks when distributing the client publicly.
